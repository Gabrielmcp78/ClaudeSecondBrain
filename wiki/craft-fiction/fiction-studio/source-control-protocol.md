# Fiction Studio — Source Control Protocol

*Governs source authority, drift prevention, and rewrite authorization for all Fiction Studio project work (String Theory, BURNThrough / The Aegis Cycle, Latency Zero, and any future manuscript project). Read this after the 7-step startup sequence and `master-system.md`, before any fiction diagnosis, continuity, assembly, or revision work — per `wiki/_meta/agent-protocol.md`'s Fiction Studio Enforcement clause.*

*Consolidated 2026-07-25 from eight prior standalone notes (`wiki/agent-control/*.md`, `wiki/projects/fiction-studio/shared-editorial-operating-knowledge.md`) written 2026-07-23. Those files are superseded by this article; their content is preserved below without loss.*

## 1. Classify the artifact before using it

Every Fiction Studio object an agent touches falls into one of these classes. Determine class before quoting, revising, assembling, or judging.

- **Canonical manuscript** — approved source prose. Read before quoting, revising, summarizing, or judging current canon.
- **Experimental draft** — noncanonical exploratory prose or options material. May be useful, but stays labeled experimental until explicitly approved.
- **Approved – Not Assembled** — approved working artifact not yet merged into the canonical manuscript. Do not treat as canon or assemble without explicit instruction.
- **Visual companion** — design, Canva, map, board, or other reference aid. Never source prose unless explicitly stated.
- **Secondary critique/reference** — editorial critique, summary, beat outline, prior answer, or SecondBrain note. Helpful context, not manuscript source.
- **Submission artifact** — packaged or cleaned reading draft prepared for a purpose. Must not silently replace canonical source.
- **Control artifact** — file-control sheet, status ledger, change log, decision registry, task ledger. Update only after verifying the live/native control surface and explicit authorization.
- **Unknown** — anything without clear status. Stop and verify before action; default to `Unknown - Verify Before Use`, never promote from memory alone.

## 2. Decision tree

1. If it is the canonical manuscript source, it can be used as prose source after direct verification.
2. If it is experimental/options material, label it experimental and do not treat it as canon.
3. If it is `Approved - Not Assembled`, treat it as approved working material but not canonical manuscript.
4. If it is a visual companion, use it only for visual/reference context unless the user explicitly says otherwise.
5. If it is critique or summary, use it only as secondary interpretation, not as source prose.
6. If it is a file-control artifact, update only after verifying the live/native control surface and explicit authorization.
7. If status is unknown, stop and verify before action.

## 3. Drift controls

- Do not infer missing bridge material, chapter status, or latest revision state.
- Do not normalize names, spellings, or terminology without authorization.
- Do not collapse experimental and canonical layers.
- Do not let critique language become prose by accident.
- Do not judge submission readiness before separating accidental scaffold labels from manuscript text.
- A newer timestamp does not automatically mean canonical.
- A cleaned reading draft does not automatically replace source manuscript.
- A critique does not authorize rewrite.
- A board/readiness report is not a manuscript revision.
- A file visible in Drive is not necessarily the right source.
- A connector write capability is not the same thing as edit permission.

**Known recurring risks:**

- STRING THEORY: experimental/options material can be mistaken for canonical Draft 6.7.
- STRING THEORY: reading drafts and cleaned submission artifacts can be mistaken for source authority.
- BURNThrough: approved working artifacts can be mistaken for assembled canon.
- BURNThrough: incomplete overview material can be mistaken for a complete canon bible.
- File control: uploaded Office sheets cannot always support live Google Sheets updates; native Sheets are required for reliable live control.
- Tools: Chrome/browser read context does not imply Google Docs write access; write-capable tools do not imply edit authorization.

## 4. Minimum verification before action

For any substantive project task, record: active project, source file or Drive file used, artifact class, date/modified time if available, user-authorized operation, output created or updated, unresolved verification gaps.

## 5. Latest / current verification protocol

Use when the user asks for "latest," "current," "newest," "approved," "canonical," "where are we," "what is next," or similar status-sensitive language.

1. Search SecondBrain for project status and prior decision notes.
2. Search Drive/local manuscript roots for the named project, chapter, scene, or artifact.
3. Compare candidates by modified time, status labels, file-control entries, and artifact class.
4. Prefer canonical source over newer experimental material unless the user asks for experimental/latest options.
5. State the basis for the selection in the response.
6. If multiple plausible candidates exist, report them with status labels instead of choosing silently.

Response language: `Canonical source verified: ...` / `Newest experimental material found: ...` / `Secondary/reference material found: ...` / `I did not find a current file-control confirmation for ...` / `This is memory-derived and should be reverified before edit/assembly.`

**Verification bar:** For low-risk summary work — current source path or Drive file identified, artifact class clear, no obvious conflicting newer candidate. For revisions, assembly, readiness judgment, or file control — source file opened or text retrieved, target scope verified, exact authorization confirmed, output scope labeled, status impact recorded.

**Common failure mode:** the system often remembers correct prior decisions, but those decisions can be stale. Memory should tell agents where to look and what traps to avoid; it should not be treated as the live file state.

## 6. Rewrite authorization protocol

Use before changing manuscript prose or creating revised prose that might be mistaken for source.

**Authorization levels:** Discuss only (answer/explain/summarize) → Diagnose (critique without changing prose) → Plan (revision plan/beat map/edit list, no new prose) → Draft experiment (noncanonical exploratory prose) → Surgical revision (a clearly bounded passage or scene) → Assembly (integrate approved material into a canonical or working manuscript file) → File-control update (change status/metadata in a control index).

**Required before drafting or revising:** target project, exact chapter/scene/passage, source text to use, desired operation, whether the output is canonical/experimental/recommendation-only, whether any live document should be modified.

**Interpretation rules:**

- A critique attachment is not rewrite authorization.
- A request for a readiness judgment is not rewrite authorization.
- "Proceed" depends on the immediately preceding proposed action; do not extend it to assembly or canonization.
- "Green light to get it done" authorizes the named documentation/control task in context, not manuscript prose changes.
- If the user asks for a "draft experiment," label it draft experiment only.

**Output labeling:** every revised-prose output states project, chapter/section range, pass type, source used, canon status, date, and whether word/count scope was verified.

**Stop conditions:** source text is missing; requested scope is ambiguous; canonical versus experimental status is unclear; two files conflict; the user seems to expect a live edit but no exact target is confirmed.

## 7. Shared editorial posture

- Treat the manuscript as the authority, not the agent's memory of it.
- Protect the author's explicit source-control status.
- Distinguish diagnosis from revision, revision from assembly, and assembly from canonical approval.
- Do not make invisible prose changes.

**Critique handling:** identify it as secondary material → extract actionable craft signals → retrieve the relevant manuscript scene → ask or infer only the operation explicitly requested (plan/compare/diagnose/revise) → if revising, label the output and canon status.

**Revision output discipline:** state what source was used, what changed at the level of craft/function, what was deliberately preserved, whether the result is canonical or experimental, what verification was performed.

**Readiness assessments:** separate secretarial/document-hygiene defects from artistic readiness. If accidental labels, notes, or production scaffolding appear, classify and clean only the authorized artifact before judging the work.

**Counts and scope:** use like-for-like boundaries. Do not compare a partial pass to a compiled chapter and describe the difference as bloat or compression without checking scope.

## 8. Artifact status ledger template

Use this template for project files that agents may cite, edit, assemble, or evaluate.

**Status values:** Canonical Manuscript · Experimental Draft · Options Pass · Approved - Not Assembled · Submission Artifact · Visual Companion · Secondary Critique / Reference · File-Control Index · Archive / Backup · Unknown - Verify Before Use.

| Field | Required note |
| --- | --- |
| Project | STRING THEORY, BURNThrough, or other project name |
| File title | Exact title from local path or Drive |
| File id/path | Drive id, local absolute path, or both |
| Status | One status value above |
| Scope | Chapter, section, scene, or whole-project range |
| Last verified | Date and verifier/agent if known |
| Source relationship | Canon source, derivative, cleanup, experiment, reference, or companion |
| Allowed operations | Read, summarize, critique, revise, assemble, update metadata, etc. |
| Forbidden operations | Any action requiring fresh authorization |
| Notes | Counts, known drift, duplicate artifacts, or next operation |

Default rule: if status is not known, treat the file as `Unknown - Verify Before Use`. Do not promote it to canon, approved, assembled, or current from memory alone.

## 9. Agent startup checklist for fiction tasks

1. Start with SecondBrain (the 7-step startup sequence in `agent-protocol.md`).
2. Identify the active project and current source-control context.
3. Separate canonical manuscript, experimental draft, approved-but-unassembled artifact, visual companion, and secondary critique/reference material.
4. Verify the current source file before using memory for any live prose, status, or latest-revision claim.
5. Confirm the requested operation: answer, critique, plan, revise, assemble, file-control update, or documentation update.
6. Confirm authorization before changing manuscript prose, status labels, canonical assembly, file-control sheets, or Drive/Docs contents.
7. Record output scope in the file name and response text: project, chapter/range, pass type, canon status, date, and whether counts were verified.
8. If drift appears, stop inference and return to SecondBrain plus current source verification.

Hard rule: memory can guide procedure and prior decisions, but it is not a substitute for checking current files when the user asks for latest, current, approved, or canonical material. Permission boundary: a tool may be write-capable while the specific edit is still unauthorized — always separate capability from permission.

## 10. Drive Docs and Sheets tooling knowledge

A selected browser tab provides read context, page title, visible text, or URL — it does not by itself prove an agent can write to the underlying document. Before promising or performing document edits, inspect the available tools in the current session; write-capable surfaces may include SecondBrain or Google Drive document append/replace/batch-update tools, but availability changes by session. Two separate questions must both be true before editing: is there a write-capable tool available, and is the requested edit authorized?

**Safer edit workflow:** identify exact Drive file or document id → retrieve current document text or target paragraph/range → confirm exact target scope → apply append, replace, or structured batch update → reread the changed area → report what changed and what was not changed.

**Google Sheets / file control:** live file-control updates should use native Google Sheets. Uploaded Office spreadsheets may display in Google Drive but fail operations that require native Sheets structure — if a tool reports an operation unsupported because the document must not be an Office file, treat the uploaded spreadsheet as backup only and convert/import to native Sheets before live control updates.

**Manuscript caution:** even when document-write tools exist, Fiction Studio manuscript prose remains protected unless the current task explicitly authorizes the edit.
