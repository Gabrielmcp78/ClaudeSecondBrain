Quick Matrix
01
Phase One
Conception & Clarity
Before a single file is created

This is the phase everyone skips and then suffers for. The output isn't code — it's certainty. Certainty about what problem you're actually solving, who it's for, what success looks like, and whether it's worth building at all. In an AI-augmented workflow you can use an agent session to rubber-duck this into clarity before committing a directory structure.

Entry Condition
You have an idea, a frustration, or a commission.
No code exists. Maybe a napkin note. Maybe a voice memo. The idea is ambient.
  • Define the irreducible sentence. One sentence. What does it do, for whom, and why now?
  • Articulate the core problem, not the solution. Separate "what I want to build" from "what problem that solves."
  • Map your distribution path. App Store? Direct download? Web app? CLI? API-only? Decide this now — it determines everything from architecture to naming.
  • Identify the single success metric. Not 5 metrics. One. What happens if this works?
  • Technology posture decision. Native macOS? Web? Electron? Node CLI? Python service? This is architecture ground zero.
  • Competitive/prior art scan. Does this exist? What's the gap you fill?
  • Scope boundary. Write down what this does NOT do. V1 scope kills more projects than anything.
  • Memory deposit. Add the project seed to your Neo4j/memory graph before proceeding.

✓ Exit Gate — Phase 1 Complete When:
You can answer in 60 seconds: what it is, who it's for, how it ships, and what "done" looks like.
If you can't do this, do not proceed. This is the most important gate in the entire lifecycle.
02
Phase Two
Foundation & Architecture
The skeleton that everything else hangs from

Foundation is where your decisions ossify. A bad architecture decision here costs 10x to fix in Phase 3 and 100x in Phase 4. Spend real time here. The modern AI-augmented workflow means you can spin up scaffolds instantly — but that speed is a trap. Think before you scaffold.

Entry Condition
Phase 1 exit gate passed. Problem defined. Distribution path chosen.
  • Directory scaffold at /Volumes/Ready500/DEVELOPMENT/[project-name]. Conventional structure from day one.
  • Version control initialized. git init, .gitignore configured, initial commit. Remote (GitHub/GitLab) created immediately.
  • Environment strategy. .env.example, secrets management, no hard-coded credentials ever.
  • Dependency selection. Only officially maintained, production-level libraries. Each dependency is a contract — evaluate it as one.
  • Architecture Decision Records (ADRs). One markdown file per major structural decision. Why this, not that. Future you will thank present you.
  • README skeleton. Write the README before the code. It forces architectural clarity.
  • Data model first-pass. Even rough — what are the core entities and their relationships?
  • Authentication/security posture. If any user data, credentials, or network calls exist, decide your security model now.
  • Testing strategy declaration. What will you test? Unit? Integration? E2E? Decide the level, even if minimal.
  • CI skeleton. Even a stub GitHub Actions workflow. The habit matters more than the completeness.
For AI-augmented builds: Use Context7 MCP to fetch current SDK docs before writing any integration code. Your training data has a cutoff. The SDK doesn't care.

03
Phase Three
Active Development
Where the actual work lives

Development is not linear. It's iterative spirals. You build, you discover, you adjust. The discipline isn't in following a waterfall — it's in never letting debt accumulate silently. In an AI-augmented workflow you can generate code at extraordinary speed, which means your quality enforcement must be equally aggressive.

Entry Condition
Foundation complete. Architecture documented. Repo initialized.

The Development Loop — run this cycle continuously:

  • Feature branch per unit of work. git checkout -b feature/[name]. Never commit to main directly during active development.
  • Write tests before or alongside code, not after. Even basic assertions count.
  • Commit atomically and with intention. Each commit is one logical change with a descriptive message. Your git log is documentation.
  • No placeholder logic. If a function exists, it works completely. TODOs in shipping code are technical debt invoices.
  • Inline documentation as you go. Every function: purpose, parameters, failure conditions. Don't save this for later — later doesn't come.
  • Dependency audit at each new addition. Do you actually need this? Is it maintained? Does it bring transitive vulnerabilities?
  • Daily or per-session memory deposits. Add architectural decisions and significant insights to Neo4j. Cross-reference between projects when patterns emerge.
  • Regular integration testing. Don't mock your integrations indefinitely. Wire the real service early and let reality correct your assumptions.
  • Error handling is not optional. Every external call, every file operation, every parse — wrapped and handled.
  • Feature flags for anything experimental. Keeps main stable while you explore.
The AI-Augmentation Trap: Generated code feels complete but often isn't. Every AI-generated function needs the same scrutiny you'd give to code you wrote yourself. Speed of generation ≠ quality of output. Review like an adversary.
Gabriel's Rule: If you're writing code you don't understand, stop. Understand it first. The speed cost is 20 minutes. The debt cost is 20 hours.

⟶ The Most Important Transition in the SDLC

Development → Staging

This is the line most solo developers blur, and it costs them enormously. Development is where you build. Staging is where you verify. The moment you say "this feature is done," you are not in Development anymore — you are making a claim that must be tested.

✓ Exit Gate — Development → Staging When:
All planned V1 features are implemented (not nearly implemented). No known broken paths. Tests pass. No uncommitted changes. Documentation reflects actual code.
The single most common mistake: entering staging with "just one more thing to fix." That way lies infinite staging loops. If it's not done, it's not done. Stay in Development.
04
Phase Four
Staging & Verification
You're not developing anymore. You're proving it works.

Staging is where your development claims meet reality. The environment should mirror production as closely as possible. The mindset should shift from builder to adversary. You are no longer adding — you are testing and hardening. Any code written in staging that isn't a bug fix means you exited Development too early.

Entry Condition
All V1 features complete. Tests pass. Clean git state. Merged to a staging or release-candidate branch.
  • Deploy to a staging environment that matches production. For web: a real server/CDN, not localhost. For macOS app: a notarized or ad-hoc signed build on a clean machine.
  • Full happy-path run-through. Execute every core user flow as if you're a new user. No shortcuts.
  • Edge case and error path testing. What happens with bad input? Network failure? Empty states? Invalid credentials?
  • Performance profiling. Does it actually perform at acceptable speed with real data volumes?
  • Security review. Check exposed endpoints. Validate auth. Review secrets handling. Scan for obvious vulnerabilities.
  • Beta cohort (even 2-3 people). External eyes catch things your familiarity blinds you to. For indie work, a trusted inner circle suffices.
  • Documentation accuracy audit. Does the README accurately describe the current state? Does the API reference match actual behavior?
  • Accessibility and compatibility check. Target OS versions, screen sizes, input methods — whatever your distribution context requires.
  • Crash and error monitoring setup. Before launch, not after. Sentry, Crashlytics, or equivalent — wired and verified.
  • Rollback plan documented. If the release breaks something, how do you revert? The plan should exist before you need it.
  • Release notes drafted. What changed? What's new? What's known? Write this during staging when the details are fresh.
Bug triage discipline: In staging, every bug found gets severity-classified before being fixed. P0 (blocks launch), P1 (degrades experience significantly), P2 (minor, can defer). Only P0s and P1s block a release. This prevents perfectionism from trapping you in staging forever.

⟶ The Gate That Protects Your Reputation

Staging → Release

The question is not "is this perfect?" It is "does this do what I said it would do, without breaking things it shouldn't break, for the people I said it's for?" If yes: ship. Perfection is a staging trap. Users need the thing that mostly works today more than the perfect thing that never arrives.

✓ Exit Gate — Staging → Release When:
Zero P0 bugs. All P1 bugs fixed or explicitly deferred with documentation. Beta feedback addressed or triaged. Monitoring wired. Rollback plan exists. Release notes written.
05
Phase Five
Release & Distribution
The ship leaves the harbor

Release is an operation, not a moment. The actual deployment is the smallest part. The distribution infrastructure, the announcement, the support readiness — that's what determines whether anyone actually uses what you built. For your indie/direct distribution model, you own this entire stack.

Entry Condition
Staging exit gate passed. All release assets prepared. Distribution channel ready.
  • Tag the release in git. git tag -a v1.0.0 -m "Release: [description]". Every release gets a tag. Non-negotiable.
  • Build release artifacts. Production build, signed and notarized (macOS), or minified/bundled (web), or packaged (CLI/Python).
  • Staged rollout where possible. Even 10% → 50% → 100%. Lets you catch problems before they're universal.
  • Distribution channel deployment. GitHub Releases, App Store submission, Gumroad, direct download, npm publish — whatever your path.
  • Monitoring confirmation. Verify Sentry/monitoring is receiving events in production before announcing.
  • Announcement / launch communication. Prepare the story: what it is, who it's for, how to get it, what comes next.
  • Support channel ready. Email, GitHub Issues, Discord — however you receive feedback. It must exist before launch.
  • CHANGELOG.md updated. The public record of what changed. Linked from the README.
  • Documentation published. Not just written — published, accessible, findable.
For macOS distribution: Notarization via xcrun notarytool is required for Gatekeeper approval. Budget 2–15 minutes per build. Test the notarized build on a machine where you've never installed the app.
GitHub Releases Xcode Archive / notarytool Gumroad / Lemon Squeezy Netlify / Vercel Homebrew (CLI tools) Sentry (confirm live)
✓ Release Complete When:
Artifact is publicly accessible. Git tag exists. Monitoring is confirmed live. CHANGELOG updated. Announcement made. Support channel exists.
06
Phase Six
Post-Launch Operations
The work that makes the work matter

Most indie projects die here. Not from technical failure — from abandonment. The post-launch phase is where you transition from builder to operator. The discipline is responding without thrashing: staying engaged with users and feedback without letting every bug report become an emergency redirect.

  • 48-hour monitoring watch. After any significant release, actively monitor crash reports, error rates, and user feedback for the first 48 hours.
  • P0 patch protocol. If a critical bug surfaces post-launch, patch within 24 hours. Document the post-mortem. Update the process to prevent the class of error.
  • User feedback aggregation. Collect everything. Tag by theme. Don't triage in real-time — batch it. Weekly is fine.
  • Analytics review (first 2 weeks). Are people using what you thought they'd use? Where are they dropping off? What's actually getting used?
  • Known issues log maintained publicly. GitHub Issues or equivalent. Users who can see you know about a problem forgive much faster.
  • Dependencies audit (monthly). Security updates, deprecations, breaking changes in upstream packages.
  • Memory graph update. What did you learn from this release? Add it as institutional knowledge. Future projects benefit.
The Solo Operator's Trap: You will want to immediately start the next big feature. Resist for 2 weeks. Let the release breathe. The feedback that comes in the first fortnight is the most valuable data you'll ever have about V1.
✓ Post-Launch Stable When:
No open P0s. Error rate is stable or declining. Feedback is aggregated and triaged. You have a clear picture of what users actually need versus what you built.
07
Phase Seven
Iteration & Evolution
The spiral continues — but with better inputs

Iteration is not a restart. It's Phase 3 with better information. The architecture exists. The foundation holds. Now you build on reality instead of assumptions. The discipline of iteration is prioritizing ruthlessly and scoping each cycle tightly — because the temptation to add everything users asked for is how products become unmaintainable.

  • Iteration planning from feedback data. What did users actually ask for most? What causes the most friction? Let the data drive V1.1 priorities, not your instincts alone.
  • Maintain the Phase 3 loop. Feature branch → implement → test → review → merge. Discipline doesn't diminish in later cycles.
  • Refactor debts addressed explicitly. Schedule technical debt like a feature. If it doesn't go on the board it doesn't get done.
  • Architecture evolution documented. When the architecture needs to change (and it will), write an ADR. "We changed X because Y, and it means Z."
  • Breaking changes handled with versioning. Semantic versioning is a promise to your users. Keep it.
  • Deprecation notices before removal. If you remove a feature or API, announce it one version before it disappears.
  • Each iteration cycle ends with a release. Even minor releases. The discipline of the full cycle compounds over time.
The compound effect: Each completed cycle — Conception → Release → Post-Launch → Iteration — leaves the codebase stronger, the documentation richer, and your intuition sharper. This is why experienced builders ship faster, not because they skip steps.

The meta-rule for solo/indie development: Every phase has exactly one job. The moment you're doing the next phase's job inside the current phase, you've broken the cycle. Development writes code. Staging breaks it. Release ships it. Post-launch listens. Iteration responds. These are not suggestions — they are the load-bearing walls.
